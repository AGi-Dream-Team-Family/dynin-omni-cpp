# Fidelity/speed receipt, 2026-09-22

Ten plain-register sentences (`bench/sentences.txt`), each run through
`dynin-t2s-kvblock --compare` at three schedules on one laptop GPU. Wavs
were written to disk only; no speakers, microphone or camera were used.

This receipt replaces an earlier one that was measured with a build in
which the diffusion architecture had no KV cache (every `llama_decode()`
call fell back to `llama_encode()`, so each windowed step attended only to
the tokens inside its window). Those numbers are withdrawn. Every run below
used binaries built on 22 Sep 2026 from the source tree later committed
as `145929e`, a pre-release revision of the patch now in `patches/` (see "Tool versions"
for exactly how the two differ), and every one of the 30 run logs contains
the cache allocation line

```
llama_kv_cache: size = 2048.00 MiB (  2048 cells,  32 layers,  2/2 seqs), K (f16): 1024.00 MiB, V (f16): 1024.00 MiB
```

and no `cannot decode batches with this context` line.

## Machine state

No compile job (`cl.exe` / `nvcc.exe` / `cmake.exe` / `ninja.exe`) and no
other process holding GPU memory was present at any point checked during
the run (spot-checked repeatedly from launch to completion, about 38
minutes). GPU memory was 181 to 213 MiB before and after the run, and about
7.7 to 8.1 GB while `dynin-t2s-kvblock` was resident and generating.

## Commands

The runs were driven by `bench/fidelity_bench.ps1` with `-Seed 42`. Each
run is equivalent to:

```
dynin-t2s-kvblock -m <dynin.gguf> --u2s <emova_u2s.gguf> \
    --text "<sentence>" \
    --steps <48|96> --block <128|16> --kv-margin 32 --cfg 2.5 --seed 42 \
    --out <run_dir> --wav --compare \
    --whisper-cli <whisper-cli> --whisper-model <ggml-base.en.bin>
```

Three arms: (block 128, steps 48), (block 128, steps 96), (block 16,
steps 48), with `--kv-margin 32` and `--cfg 2.5` in all three. All 30 runs
exited 0 and wrote `match.json`, `timing.json` and both Whisper
transcripts.

Raw data: every run's full `run.log`, `match.json` and `timing.json`, plus
the bench script's `raw_runs.json` and `summary.csv`, are in
`receipts/raw/fidelity_2026-09-22/`. The directory part of every absolute
local path in them has been replaced with `<path>/`; nothing else was
changed. The wavs are not included.

## How the numbers were taken

- `exact ms` / `windowed ms`: `total_ms` from each run's `timing.json`
  (the diffusion block loop only; model load, the one-off unconditional
  decode, rendering and Whisper are outside it).
- `unit match` and `first div`: `exact_match_fraction` and
  `first_divergence_index` from `match.json`.
- Word overlap: the value `dynin-t2s-kvblock` prints on its
  `[DYNIN-T2S-CHECK ... word_overlap=...]` line, the fraction of the
  sentence's unique words (lower-cased, split on non-alphanumeric
  characters) that appear in the transcript. At the time of these runs,
  `bench/fidelity_bench.ps1` recomputed overlap itself from a regex that
  stopped at the first apostrophe in a transcript, so the per-run file it
  wrote (`receipts/raw/fidelity_2026-09-22/raw_runs.json`) reports 0.125
  for sentence 10 in the four runs where the transcript contains "light's",
  and the means in its `summary.csv` are computed from those values:
  0.5671 exact (block 128 / 48), 0.8875 exact and 0.8875 windowed (block
  128 / 96) and 0.6734 exact (block 16 / 48); the other columns are
  unaffected. The figures in this receipt use the tool's own printed value
  instead, which is in each run's `run.log`. The script was fixed after
  these runs: the version in `bench/` takes the overlap from the tool's own
  `word_overlap=` field. The fixed script has not been used for a full
  bench run.
- Means are over the ten sentences. Speedup is mean exact ms divided by
  mean windowed ms.

## Summary (quiet machine, n = 10 sentences per arm)

| arm | mean exact ms | mean windowed ms | speedup | mean unit match | mean word overlap (exact) | mean word overlap (windowed) |
|---|---|---|---|---|---|---|
| block 128 / steps 48 / margin 32 | 33915.9 | 3846.2 | 8.82x | 0.8437 | 0.5796 | 0.6613 |
| block 128 / steps 96 / margin 32 | 72672.8 | 9749.6 | 7.45x | 0.9098 | 0.9375 | 0.9250 |
| block 16 / steps 48 / margin 32 | 34683.3 | 4695.1 | 7.39x | 0.6417 | 0.6984 | 0.7402 |

Per-run speedup ranged from 6.99x to 9.94x (block 128 / 48), 6.08x to
8.16x (block 128 / 96) and 7.01x to 7.78x (block 16 / 48). Every run made
49 forward passes at 48 steps and 97 at 96 steps (one unconditional decode
plus one per step), on both paths.

Reading:

- **Speed.** The windowed path was 7.4x to 8.8x faster on the means. The
  number of positions decoded per run falls by 10.7x (block 128 / 48:
  4,833 vs 51,504), 8.1x (block 128 / 96: 13,281 vs 107,616) and 8.4x
  (block 16 / 48: 6,099 vs 51,504); the measured ratios are below those.
- **Unit agreement.** At block 128, 7 of 10 sentences produced identical
  unit ids on both paths at both 48 and 96 steps. The other three are
  sentences 4, 5 and 10, the only ones whose prompts are long enough (991
  or 992 `[iPAD]` positions in the 1,024-position text block, against 993
  to 995 for the rest) that the first one or two prompt tokens fall
  before the window start at position 993 and are read from the cache as
  computed at the block's step 0. At block 16 no sentence matched exactly:
  the windows of the second and third blocks start at positions 1,009 and
  1,025, so part or all of the prompt is read from step-0 cache cells.
  (Pad counts were read from the pad-mask log line of the earlier no-cache
  build, which builds the prompt the same way; the KV-cache path does not
  print that line.)
- **Word overlap.** Step count moved intelligibility more than windowing
  did: the dense path averaged 0.58 at 48 steps and 0.94 at 96 steps. The
  windowed path scored higher than the dense path at block 128 / 48 and
  block 16 / 48 and 0.0125 lower at block 128 / 96. With ten sentences and
  a base-size Whisper model as the scorer, differences of this size do not
  show that either path is better. Several transcripts are Whisper
  mishearings of audio that is identical on both paths (for example
  sentence 1 at block 128 / 96, "cattle" for "kettle", from identical unit
  ids).
- **Vocoder backend.** The wavs were rendered with the CPU generator in all
  30 runs: at the time of these runs the tool gated the CUDA generator on
  an int16 max-difference rule (tolerance 8) and the measured difference
  was 28 to 242 int16 steps, so it fell back to the CPU. That rule has since
  been replaced by a signal-to-error ratio gate (40 dB), under which the
  units-to-speech smoke run in `receipts/smoke_2026-09-25.md` measured
  57.15 dB and used CUDA; the wavs and transcripts here were not
  re-rendered. `enc_p` and the flow ran on CUDA in every run. This
  does not affect any timing above (rendering is outside `total_ms`).
